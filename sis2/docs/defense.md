
Первая команда демонстрирует новый сбор 200 строк. Вторая воспроизводит 400 архивных позиций, показанных в отчёте. Независимые команды для запуска Producer и Consumer приведены в README.

## Вопросы для репетиции

1. **Что в данном случае называется прослушиванием?** API возвращает готовый счётчик за период. Одна строка — позиция рейтинга. Число уникальных слушателей из неё определить нельзя.
2. **Как Consumer понимает, что пора завершаться?** Producer сохраняет offsets после подтверждений. Consumer читает сохранённый набор, сверяет run ID и индекс и завершает цикл после нужного числа строк. Время ожидания ограничено.
3. **Чем отличаются две защиты от дубликатов?** Идемпотентный Producer защищает от повторной записи при повторе отправки клиентом. Повторный запуск приложения создаёт новые сообщения. Составной первичный ключ и проверка содержимого отдельно защищают SQLite.
4. **Почему валидация предшествует преобразованию типов?** В исходном JSON число, строка и логическое значение различимы. Преждевременное приведение типов могло бы скрыть ошибку. Посмотрите тест с null, 1.0, строкой и true.
5. **Как проверить отсутствие порчи данных при повторной загрузке?** Сравнить количество строк и SHA-256 всех полей в однозначном порядке. Один COUNT не выявил бы замену значения.
6. **Почему у одной песни несколько рангов?** Один recording_mbid может соответствовать нескольким исходным позициям с разными данными релиза или обложки. Для сравнения между окнами pivot выбирает лучший ранг. В базе сохраняются все позиции.
7. **Что означают 24,9%?** Это доля позиции BTS на первом месте среди прослушиваний, попавших в недельный топ-100 исполнителей. В этом списке есть и другая строка с именем BTS без идентификатора.
8. **Как сравнить неделю и месяц?** Разделить каждое число на фактическую длительность окна либо сравнить доли внутри каждого списка. Два интервала показывают различие между выборками и не устанавливают причину изменения.
9. **Как продемонстрировать практическое изменение?** Сменить `--count 100` на `--count 50`, предсказать 200 сообщений и проверить новую сводку. В SQL добавить условие `rank <= 10` и сравнить суммы для одной категории и одного периода.
